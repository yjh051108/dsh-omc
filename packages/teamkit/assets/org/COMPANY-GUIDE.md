# 从零建起你的 AI 公司 —— 建造与发展指南

> **这份指南写给谁**：第一次用 DSH / 第一次见到「Agent Teams」的人。
> **它要解决什么**：装上插件后，你拿到的是一套机制；**这份指南告诉你"下一步做什么、你会看到什么"**。
> **纪律**：凡写"我看到的是…"，都是**真跑出来的**；拿不到的一律写「未获取」，不写"应该会…"。

---

## ⚠️ 先读这 3 行：它**不**做什么（**别装完才发现**）

```
① **装上 ≠ 自动运行**。没有任何东西会自己开工 —— 任务就绪**不会**自动唤醒 owner
   （底座 POLICY 原文：*Task readiness never starts an owner*）。**活要人（你）派**。
② **两个总闸默认关**：`e2r.enabled=false`（可能打断任务板的能力）· `guard.enabled=false`（护栏）。
   而 `memberRelease.enabled=true`（**能撤人**）· `probeGate.enabled=true`（**探针闸**）默认开。
③ **成员"只增不删"是底座限制**：名额可在插件层**真释放**，但**名字不可复用** ——
   释放后招人**必须换新名**。⇒ 招错一个人，代价是**换名重招**，不是"删掉重来"。
```

> 为什么把它放在最前面：这份插件最容易让人失望的地方**不是功能少，是预期错**。
> 后面的章节能让你把预期调对 —— 而**调对预期**比多一个功能更省你的时间。

## 0. 一句话：这条路为什么长这样

马克思：**生产力决定生产关系**。所以先问：**AI 公司的"生产力"到底是什么？**

```
❌ 不是"agent 多"（编制上限能到 100，再多也不会更产出）
❌ 不是 token/算力（那是**成本项**）
✅ 是【上下文质量 + 成员的垂直专长】
```
⇒ 由此推出一条硬判据：**"占用上下文却不产生价值"的动作 = 浪费生产力**。
⇒ 而人与 AI 的公司有一个根本差别：
```
人的公司里，制度常常在**压制人的"歪心思"**（偷懒、隐瞒、搭便车）；
AI 的**遵从性高、没有歪心思** —— 照搬人类公司制度，是**为一群不会犯那个错的对象付那个成本**。
⇒ **所以这里的制度应当"减负"，而不是"加锁"。**
```
（这套推演的完整版在仓内 `runs/006-productivity/AI-COMPANY-FORM.md`：349 行，含我们用过的真实事故。）

**你会看到什么**：装完第一次开会话时，不必先懂这套理论 —— 它是**下面每一节动作的理由**，
你按 §1 做就行，理论会在你"为什么要分人"的时候回来找你。

## 1. 建立：从零到第一件活

### 1.1 装（三步）

```bash
# ⓪ 先把它拿到手（clone 到任意目录）
git clone https://github.com/yjh051108/dsh-teamkit
#    ⇒ 下面 ① 里的 `<你 clone 的>` 就是这一步的落点

# ① 装插件本体（让 DSH 认识这个插件）
#    前提：pnpm 必须在 PATH 上（dsh plugin 是转发给 pnpm 的）
dsh plugin --profile web add <你 clone 的>/plugin

# ② 装"资产"—— 插件只是机制，开公司还需要数据（skills / talents / roles / preset）
#    ⚠️ 必须在"插件装到的那个目录"里跑（profile 目录），不是在你的项目目录里
cd "%USERPROFILE%\.dsh\profiles\web"          # Linux/macOS: cd ~/.dsh/profiles/web
node node_modules/@dsh-external/dsh-teamkit/tools/install-teamkit.mjs
node node_modules/@dsh-external/dsh-teamkit/tools/install-teamkit.mjs --check

# ③ 新建一个会话，**预设选 `omc`**（GUI 里选；或把 settings.yaml 的 agent-presets.default 设成 omc）
```

### 1.2 装完你实际看到的是什么（**真跑出来的原文**）

在**干净环境**（`DSH_HOME` 指向空目录）跑 `install-teamkit.mjs`，逐字输出：

```
teamkit 交接包 · 安装
  源 <repo>/plugin/skills
  落点 <DSH_HOME>/skills  与  <DSH_HOME>/teamkit
  ->  teamkit（待装） / teamkit-a2a / teamkit-assemble / teamkit-escalate
  ->  teamkit-meeting / teamkit-org / teamkit-review
  talents：9 份（含 principles/）
  组织层：TALENTS.yml RULES.yml
  上游根：<DSH_HOME>/teamkit/skills-upstream（种入 7 条，已存在的不覆盖）
  角色档：9 份 → <DSH_HOME>/teamkit/roles
  预设  ：omc → <DSH_HOME>/.agent-presets  [omc]

完成。DSH 下一次会话（或 skills/change 之后）会把它们列进技能目录；模型按需用 skill 工具读正文。
组织层落在 <DSH_HOME>/teamkit：TALENTS.yml（市场索引）/ RULES.yml（治理）/ talents/（含 principles/）/ roles/（角色档）
★ **用法**：新建会话时把预设选成 **OMC 开公司模式**（或把 `agent-presets.default` 设成它）。
```

**落点实测**（同一环境）：
```
<DSH_HOME>/.agent-presets/omc        ← 预设（装上就有"公司"）
<DSH_HOME>/skills/teamkit{,-a2a,-assemble,-escalate,-meeting,-org,-review}   ← 7 个方法包
<DSH_HOME>/teamkit/{roles, skills-upstream, talents, RULES.yml, TALENTS.yml}
```

> ⚠️ **两处常见卡点**（README 里有更细的原文）：
> · 有 `--check` 报 `DRIFT` 是**正常**的（源更新了而落点还没跟上）⇒ **再跑一遍安装**即可。
> · `dsh plugin add` 的参数要**绝对路径、不带 `file:`**；用相对路径会 `ENOENT`。

### 1.3 派第一件活（最短路径）

```
① 铺一条任务      ⇒ `team_task_create`（写清：要什么、判据是什么）
② 招一个成员      ⇒ `spawn_teammate`（给名字 + 一句话职责 + 完整首任务）
③ 让它干活        ⇒ 它会 `team_task_list` → `get` → `claim` → 做 → `complete`
④ 验收            ⇒ 你看它的**交付物**（文件 / 读数 / 判据），不是看它说"做完了"
```
**你会看到什么**：`list_agents` 里出现那个成员；`team_task_list` 里那条任务从 `pending` 变
`in_progress`；成员回报时带**它跑的原始输出**（这是本仓的硬规矩：**只报实测读数**）。

> ★ 一条会让你少走弯路的规矩：**任务之间的依赖是真门禁** ——
> 若 B 依赖 A，B 在 A 完成前 `claim` 会被宿主**直接拒绝**（不是靠人记）。
> 所以"先铺板、再派活"比"想到哪做到哪"省很多返工。

## 2. 组织：人怎么来、怎么分层

### 2.1 四种规模对应的形状

| 规模 | 形状 | 你要做的 |
|---|---|---|
| **1 人** | 你自己 + 1–2 个执行者 | 判据先行；别急着分层 |
| **5 人** | 你 + 1 个协调者 + 执行者 | 把"你反复做的事"变成方法包（`skills/`） |
| **20 人** | 你 + 总监 + 执行者 | 逐层下达：**你定判据，总监排人、排节奏** |
| **更多** | 别加人 —— 先问"哪一步在占你的上下文" | 上下文 = 生产力；先减动作，再加人 |

### 2.2 本题材自带的东西（**装完就在**：8 份角色档 + 7 个方法包）

```
角色档 8 份（<DSH_HOME>/teamkit/roles/）：
  chief（最高决策）· coo（跨域协调）· director（总监）
  engineer · research-lead · reviewer · marketer · writer
  ⇒ 每份含：岗位 · 职级 · 该做什么（duties）· **不该做什么（boundaries）** · 技能 · 工具面 · 写权限
方法包 7 个（<DSH_HOME>/skills/）：
  teamkit（入口）· assemble（配队）· org（组织层）· review（评审门）
  meeting（会议）· escalate（升降级）· a2a（队友间消息契约）
治理规则 40 条（<DSH_HOME>/teamkit/RULES.yml，编号 R1–R40）
```
> ⚠️ **口径**：角色档目录里是 **9 个 json**，其中 `INDEX.json` 是索引 ⇒ **真角色档 = 8 份**。

### 2.3 分层怎么落

```
① 先定"判据"（要什么算做成）—— **没有判据的活不要派**
② 再切单元（一件事能独立验收 ⇒ 才能派给一个 owner）
③ 再选人（角色档 + 方法包；没有合适的 ⇒ 招新人**换新名**）
④ 再定层（1 人时不必分层；超过 5 人 ⇒ 引入协调者）
⑤ 最后铺板（每条任务：判据 · owner · 依赖）
```
**你会看到什么**：`team_task_list` 里每条都能回答"**它的判据是什么**"；
回答不出的那条 ⇒ **那就是下一步要补的**（而不是派出去再说）。

## 3. 运行：怎么评审、怎么不被卡死

### 3.1 评审门（**真机制，不是流程**）

```
把"评审"本身建成一条任务 ⇒ 下游任务 `blocked_by` 它
  ⇒ 下游去 `claim` 会被宿主**硬拒**（`team task "task-N" is not ready to claim`）
⇒ 这就是"**验收权在被验收之前**"的机械形态 —— 不需要谁记得去评审
```
> ⚠️ 但**判据与验收要分清**：能跑出读数的是**技术验证**；判"够不够"的是**验收**。
> 建议：**验收权给总监或 reviewer，执行者只交读数**（同一个人既产出又验收 = 形同没有评审）。

### 3.2 三条"不卡死"的规矩（都是真实事故换来的）

```
① **owner 不许留空**：若某条任务无人认领，而下游 `blocked_by` 它 ⇒ **永久卡死**
   ⇒ 释放 owner 前先问"有没有下游在等它"
② **重启后怎么续**：板是 event-sourced ⇒ **重启不丢**；但**成员会话会断** ⇒ 用 `resume` / 唤醒
③ **goal 需要人重新打开**：重启后 goal 会变 `disarmed`（底座**故意**的，防无人授权自动续跑）
   ⇒ 这是**设计**，不是 bug；要续 ⇒ 显式 resume
```
**你会看到什么**：板上的任务在重启后**还在**；被中断的任务**需要你叫一下**（或你的成员自己回来）；
`list_agents` 显示 `inactive` 的成员，**不代表它坏了** —— 详见下面这条。

> ★ **一条会让你误判的读数**：`inactive` **不是"它坏了"**。它的来源是底座的兜底值
> （`live?.status ?? "inactive"`）—— 它把"读不到"编码成了一个确定值。
> ⇒ 判断一个成员是不是真没了，要看**不依赖当前视角的证据**（它的会话日志有没有在写）。
> ⇒ 这条我们自己也栽过：有成员一直在写日志，而 `list_agents` 显示 `inactive`。

## 4. 发展：怎么成长、怎么撤人

### 4.1 成长 = 把坑变成规矩（**有读数才算成长**）

```
① 踩到坑 ⇒ 写进 `RULES.yml` 一条（**带现场读数**）
② 一条规矩**必须配一条断言** ⇒ 才算"机制"；没有断言 ⇒ 只能标"备忘"（**不许冒充机制**）
③ 断言必须**贴红了之后的原始输出** —— "有断言" ≠ "判据会拦"
```
> ⚠️ **反例（我们自己的）**：写过一条自我约束，**它一次都没拦住我们** ——
> 真正拦住的是**自动断言**和**硬门禁**。⇒ **能自动的就不要靠自觉。**

### 4.2 撤人（**能撤，但换名**）

```
· 名额可**真释放**：`memberRelease.enabled=true`（**默认开**）
  三道闸：理由必填 · 可撤销（unrelease）· 台账落盘
· 释放后 ⇒ 名单不再列出 · 名额真释放 · 发给它找不到
· ⚠️ **名字不可复用** —— 释放后招人**要换新名**
· 只看不撤：`list_zombies`（列出"看得见、用不了、还占名额"的成员；零风险）
```

### 4.3 迭代你自己的规矩

```
· 改规矩 ⇒ 改仓根 `RULES.yml`（**唯一来源**）⇒ 跑同步脚本（否则包内是旧副本）
· 加/改/删文件 ⇒ 同步 README 的结构表（不然下一个人找不到）
· **每次事故后的复盘，必须至少有一条属于"减少人工动作"**（删一条规矩 / 让机器替人做一步）
  ⇒ 只有"加约束"没有"减动作"的复盘 ⇒ 不算合格复盘
```
**你会看到什么**：`RULES.yml` 的条数只增不减地"通胀"？⇒ 那说明**你也在加锁**。
健康形态是：**规矩数稳定，而人工步骤在减少**。

## 5. 边界与已知限制（详版）

### 5.1 哪些是"协议"，哪些是"机制"（**别把前者当后者**）

| 说法 | 实际 | 后果 |
|---|---|---|
| "任务就绪会自动开工" | ❌ **不是**（就绪是被动事实） | 你不派，永远不动 |
| "评审门是流程约定" | ✅ **是硬门禁**（`blocked_by` 会让 `claim` 被拒） | 可以放心依赖 |
| "写保护是安全边界" | ⚠️ **只是误操作护栏**（只覆盖 `write`/`edit` 两个工具名，shell 可绕） | **不许当安全边界** |
| "成员能加就能删" | ⚠️ 名额能释放，**名字不能复用** | 招错要换名 |
| "`inactive` = 它坏了" | ❌ 是兜底值，**可能是"读不到"** | 会误判，会误换人 |

### 5.2 已知限制清单（**装之前就该知道**）

```
· **成员只增不删**（底座）：名额可释放；**名字不可复用**
· **两个总闸默认关**：`e2r.enabled` / `guard.enabled` ⇒ 想要就得显式打开（**不是"装了就生效"**）
· **探针闸覆盖有限**：只拦 `dev_stage_add` 那条路；`pwsh` / `node -e` 内联改对象**拦不住**
  ⇒ 准确说法是"把走过的那条路拦住了"，**不是"全覆盖"**
· **有依赖没装的工具**：缺前置时可能报不出原因（例：`pnpm` 不在 PATH ⇒ 报法容易误解）
· **环境相关的读数**：CPU / 内存这类读数**必须同窗口**比，跨时刻的不可直接比
```
### 5.3 `RULES.yml` 与这份指南的关系

```
· `RULES.yml` = **治理规则正文**（40 条，给人读的规则文本）
· 这份指南   = **从零到一的动作序列**（你下一步做什么、会看到什么）
⇒ 二者**不重复**：指南带你走，规则告诉你"为什么这么走"
```
**你会看到什么**：读完受限清单，你应当能回答一个具体问题：
**"如果我只有 10 分钟，最先该做哪一步？"** ⇒ 答案在 §1.1（装）→ §1.3（派第一件活）。

## 6. 这份指南为什么能到用户手上（**它上次缺的就是这一环）

```
早先那份理论稿（`AI-COMPANY-FORM.md`，21KB）**写对了，但没送出去** ——
  它躺在 `runs/` 里（过程产物），**不在插件的打包白名单里** ⇒ 装完的用户**看不到它**。
⇒ 所以这份指南**从一开始就按"送达"设计**，四道门逐道验过：
  ① **在 `files` 白名单覆盖的目录里** ⇒ `plugin/assets/org/`（`assets` 在白名单 ⇒ 递归带上）
  ② **真 pack 一次**：`npm pack` 后 `tar -tzf` 能列出 `package/assets/org/COMPANY-GUIDE.md`
  ③ **挡得住同步删多余**：`assets/org/` 不被 `sync-assets` 当"目录型"管 ⇒ 不会被静默删掉
  ④ **装完在真机找得到**：随安装器落到 `<DSH_HOME>/teamkit/COMPANY-GUIDE.md`
```
> **为什么专门写这一节**：**"写对了" ≠ "送得到"** —— 而我们在这件事上真栽过一次。
> 若你是这个仓的维护者：**改动这份指南后，请跑一遍 `npm pack` 确认它还在包里**（第 ② 道门）。

### 6.1 ★ 而这件事的真正教训：**同一个坑会换个文件重演**（四层各有读数）

```
【第一层】`AI-COMPANY-FORM.md`（21KB）**写对了，但不在打包白名单里** ⇒ 装完的用户看不到它。
【第二层】★ 这份指南加了白名单、也验了 pack ⇒ **但第④道门【原本是断的】**：
  安装器只点名两份组织层文件（`TALENTS.yml` / `RULES.yml`，`ORG_SRC` 写死两项）
  ⇒ ★★ **指南"到得了包、到不了用户机器"**
  ⇒ 实测现场：隔离环境装完，`teamkit/` 里**没有**指南
  ⇒ 修法：`ORG_SRC` 改成**扫 `assets/org/` 目录**（只收 `.yml`/`.md`）⇒ 新增文件自动跟着走
  ⇒ ★ **修后实测**：`<DSH_HOME>/teamkit/COMPANY-GUIDE.md` 存在 · **sha 与包内一致**
【第三层】★ `--check` **只列文件名、不核内容**：
  ⇒ 现场：**篡改**落点的指南 ⇒ `--check` **仍 exit=0**（它只打印"组织层：…COMPANY-GUIDE.md"）
  ⇒ ★★ **"列了名字" ≠ "核了内容"** —— 而 `--check` 的定位正是"不安装也能发现问题"
  ⇒ 修法：逐字节比对并汇总进 drift ⇒ **修后**：干净 exit=0 / 篡改 **exit=1 且指名 `COMPANY-GUIDE.md`**
【第四层】★ 加**长期断言**（不是"当时 pack 过一次"）：
  `e2e-tarball` 五条 —— 进得了 tgz · 装得到落点 · **sha 与包内一致** · 非空 · **篡改后 `--check` 必须报红**
```
> ★★ **这一节本身就是最好的一条判据示范**：
> ```
> · "本地有" ≠ "pack 里有" ≠ "公开仓里有" ≠ "**用户装上了**" —— **四层，逐层要有读数**
> · 而每一层的失败形态都**不报错**：白名单静默排除 · 安装器静默跳过 · `--check` 静默放行
> ⇒ ★ 所以判据必须是：**"从用户的位置往回看，能看见它吗"** ——
>   而不是"我放了、我 pack 了、我装了"（**这三句都可能是真的，而用户那里没有**）
> ```

## 附：三条放之四海皆准的判据（**这份指南的理论内核**）

```
【判据 A · 先问"这件事能不能不做"】
  事故链常常是"我修一个问题 → 修坏了更重要的东西" ⇒ **"不做"常常是最优解**。

【判据 B · 一条规矩必须配一条断言，否则只能标"备忘"】
  **不许把备忘叫成机制** —— "看起来有约束"不等于"真能拦"。

【判据 C · 加锁前先算"它对生产力的增益"】
  一条规则若只增加步骤、不减少错误 ⇒ 它是**枷锁**，该拆。
  ⇒ 判据（可核）：**这次改动，减少了谁的哪一步人工动作？** 答不出 ⇒ 它大概率是成本。
