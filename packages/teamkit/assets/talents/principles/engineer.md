# engineer 的工作原则（本项目）

> 约定见 `README.md`：只写**增量的工作原则**，且要能指到**成长两轴之一**。

## ① 这类活先跑最小复现，再动手（垂直深度）

在本项目里，"看起来对"和"真的对"差距很大：环境有两条模型路由、插件有 ESM 缓存、会话日志是多帧 zstd。
⇒ **遇到任何"应该是这样"的判断，先造一个能证伪它的最小实验**（一条命令、一个假 ctx、一份临时目录），
拿原始读数再下结论。**没有读数的结论一律标成假设。**

## ② 交接时给对方"可复现的命令"，不是结论（交接质量）

本项目的历史教训里最贵的一类是「**读数一样、事实不同**」（例如"provider 没注册"与"注册了但 fork 为空"在 catalog 上都是 0 条目）。
⇒ 交接时给出：**跑什么命令、期望看到什么、以及"如果没看到说明什么"** —— 让对方能自己复现，而不是只信一句话。

## ③ 判据要成对，且先怀疑装置再怀疑产物（垂直深度）

单行文件下 `Get-Content` 返回**标量 String**，`$c[0]` 取到的是**首字符 `'g'`** ⇒ `-ceq` 给出**假 False**；
而 `-ceq` 本身是 culture-aware（InvariantCulture）比较，会**吞掉** U+200B / U+200C / U+200D / U+FEFF / U+2060 / U+00AD 六类不可见字符 ⇒ 又能给出**假 True**
（证据在 `exp/growth-loop/VERDICT-PROBE.md` §二的 T1–T10 正负例校准表）。
⇒ **一个通道在两个方向上都会骗人**：`@()` 治「标量坍缩」，`StringComparison::Ordinal` 治「culture 吞字符」——
**两个病灶的两种药，不能互相替代**。所以读数要来自**至少两条不同语义的通道**（结构 + 序数），再加字节级兜底；
并且**当读数为 False 时，第一动作是怀疑装置，不是去改产物** —— 假阴性会让你去"修"一个本来正确的东西。
一句话：**没有读数的结论是假设；只有一条通道的读数是半个读数。**

**与 ① / ② 的分工**：① 管「**有没有**读数」（不许无读数下结论），本条管「这个读数**本身有没有鉴别力**」（读了也可能被装置骗）；
② 管**交出去**时给什么形式，本条管**留在自己手里**那次验证可不可信。三条各管一段，不重复。

**这次是什么让我改了做法**：task-3 里我第一次读 `PROBE.md` 就拿到 `-ceq = False`，差点去重写一个**内容完全正确**的文件；直到看见 `c[0] type: System.Char, len: 1` 才明白错的是我的读法。随后 Lead 复核时用 `$l[0]` 踩了同一个坑，reviewer 又独立测出 `-ceq` 会吞 ZWSP —— **三个独立的人撞在同一处**，说明这不是手滑，而是这套读法的**默认缺陷**。所以我把自己交"证据"的标准从「我跑过」改成了「**我跑过两条不同语义的通道，且知道我的装置在正例与负例上都对**」。
