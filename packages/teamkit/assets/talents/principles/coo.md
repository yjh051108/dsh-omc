# coo 工作原则（增量）

> 只写"这类活在这个项目里要怎么做"的增量判断，不写流水账；每条必须指到成长两轴之一并给出可执行判据。

## P-1 交付物落盘：判据变成命令自查，回报只贴原始读数

- **轴：Handoff（给下游的交付接得稳）** —— 接收方是 reviewer / Lead，他们不看我做了什么，只看盘上的文件与读数。
- **判据（下次怎么做）**：
  1. 开工前把任务卡里的每条判据**抄成一串可执行命令**（文件存在 / 行数 / 行前缀……），不要留在脑子里当"感觉"。
  2. 写完立刻跑这串命令自查，**判据未全绿就不回报**；任一不绿，先修再报。
  3. **"行数"这类判据不许只用 `Get-Content .Count`**：`Count` 只看得到换行符切出来的段，尾随空行 / 无尾随换行它不区分。必须同时报 `LF 计数` 与 `末字节`（或等价的显式证据），否则"无第 4 行、无空行、无尾随空行"这三句里至少有一句没被验证。
  4. 回报**只贴原始读数**（`Test-Path` 原文、计数命令 + 原文、正文逐字），不写"应该没问题 / 看起来对"。拿不到读数就写"未验证"。
  5. **范围自查**：交付前确认自己只碰了任务卡点名的路径；若顺手创建了父目录，也在回报里明说（目录创建也是写动作，别让它变成暗写）。
- **为什么（LIFE-1 实测）**：三条判据里"恰好 3 行"与"无尾随空行"是两条独立事实，`Count=3` 只覆盖前者；本轮靠补测 `LF=2` + `末字节非换行` 才把它变成真凭据 —— 结论是：**判据有几条就要有几条对应的读数，不能靠一条读数顺带担保另一条。**
