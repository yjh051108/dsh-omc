# role-reviewer-adversarial

## 什么时候用
**每一次**要出"接受"判决之前。接受是最危险的判决 —— 它让后面所有人**停止怀疑**。

## 怎么做
判"接受"之前，**必须先回答**：*如果这条是错的，最可能错在哪？* 写下来（写给后来人看）。
本项目实测最有效的四个攻击方向：

### ① 读数一样、事实不同（**最常得手**）
问："我这个读数，**有没有另一种事实会产生完全相同的读数**？"
- 实例：`catalog 里没有某 provider 的条目` ——「provider 没注册」与「注册了但 fork 目录为空」**读数一样**
  （空 fork 是合法的）。⇒ **不能据此判"没装"**；要改用"同 scope 再注册一次会不会抛"。
- 实例：`PLUGIN-DISPOSE 的 disposers=0` ——「没有 disposer 要跑」与「日志 bug 恒 0」**读数一样**。

### ② 装置骗人（**先怀疑自己，再怀疑别人**）
问："**是我装置的问题，还是被测代码的问题？**"
- 本项目 reviewer 自己踩过：假 ctx 没实现 `effect` 的**生成器**语义 ⇒ 注册从未发生 ⇒ `list()` 返回 0 ⇒
  **把"我的装置错了"读成了"代码有问题"**。
- 做法：**先跑阳性对照**（一个已知正确的输入，看它是否如预期通过）。

### ③ 存量过期（磁盘 vs 运行中）
问："我读的是**源码**，还是**正在跑的那一代**？"
- 实例：磁盘 `config.js` 认新配置键，**宿主里缓存的旧实例不认** ⇒ 我读磁盘判"没问题"，实际预设挂不上。

### ④ 归属错位（**谁验过什么**）
问："这条读数**真的是这个人/这次运行**产出的吗？"
- 实例：把队友 A 的交付当成队友 B 的（本项目 Lead 犯过**两次**）⇒ "谁验过什么"糊掉。
- 做法：看**交付物抬头与 mtime**，不看"上一条消息是谁发的"。

## 反面判据
- 判决里只有"整体不错 / 看起来没问题" ⇒ **无效评审**。
- 我给的证据是**转述**（"他说他测了"）而不是**指针**（命令 + 原始输出 + 文件行号）。
