# 升级与退出

> **口径**：本节里的"升级"= **把决策上移**（escalation：改判据 / 裁决 / 授权），**不是 agent 的等级晋升**。
> 本区**不设"晋升"** —— 成长只有两轴：**垂直深度**（在自己的领域做到最棒）+ **交接质量**（懂得跟对应的人交接）。
> 见 `runs/005-role-skills/GROWTH.md`。

## 什么时候升级（往上一层）
- 判据本身有问题（做对了也不解决问题）→ 升级**改判据**；
- 两个队友对同一件事给出冲突结论 → 升级要**裁决**（带上两边的证据）；
- 需要碰写范围之外的东西 → 升级要**授权**，别自己扩权。

升级时把问题改写成一个**决策问题**（"在 A 与 B 之间选，代价分别是…"），不要转述一堆过程。

## 什么时候降级/收权
- 一条线超过 2 轮没有可验证产出 → 把活收回上层，或换切分；
- 团队人数比"并行块数"还多 → 撤人（人多不会更快，只会更多沟通）。

### 撤人怎么撤（**有工具，不是"没办法"**）
底座**没有** `remove/delete` 成员的方法 —— 但插件**补了这条路**（`plugin/lib/release.js`）：
| 工具 | 什么时候出现 | 干什么 |
|---|---|---|
| `list_zombies` | **默认就有**（只读） | 列出"看得见、用不了、还占名额"的（`phase=failed` / 长期没活动的） |
| `release_member {name, reason}` | 要 `memberRelease.enabled=true` | 释放：名单不再列出 · **名额真释放** · 发给它找不到 |
| `unrelease_member {name}` | 同上 | 撤销释放（误操作回退），幂等 |
**三条必须知道的**（我实测出来的）：
1. **`reason` 必填**（schema 层就拦：这是给对方也是给未来的你的记录）；
2. **名字不可复用** ⇒ 释放后招人**要换新名**（底座永久占位）；
3. **日志里抹不掉**（journal 是 event-sourced）—— **抹掉等于伪造历史**，所以别指望"删干净"。
⚠️ **撤人不搬活**：成员走了**不会**自动释放它手上的 `in_progress` 任务 ⇒
**先 `reassign` 再撤人**，否则留下孤儿任务（`teamkit-assemble` §5 的坑 2）。
⚠️ **顺序**：`list_zombies`（先看得见）→ 确认确实用不了 → `release_member`（带理由）。
**别把"撤人"当第一手段** —— 先走下面的**纠错闭环**。

## ★ 做得不够好时：**先纠正，别急换人**（考核闭环，四步）

> **口径（委托方裁定，`GROWTH.md` §0）**：考核的用途**不是淘汰/排队**，
> 而是「**让他意识到自己在这个位置上做得不够好**，从而有动力去改自己的 **skills / SOUL**」。
> **本区不设"晋升"**；递进 = **纠错强度**，不是等级。
> 完整设计见 `runs/005-role-skills/PERF-LOOP.md`；**下面是可照做的四步**（每步**二值**，不许含糊）。

| 步 | 动作 | **二值判据** | 谁做 |
|---|---|---|---|
| **S0 预登记** | **发信号之前**，把「哪条行为不达标 + 目标读数 + **观测窗口 `T`**」写进 `reviews/<name>-perf.md` | 文件里**有那一行且含 `T`** | reviewer |
| **S1 送达** | `send_message` 给本人，记 `delivered_at` | 窗口 `T` 内有新 turn **且**它提到了判决要点 = **送达**；无新 turn = **未送达**（改走"下次 spawn 的 `prompt`"）；有 turn 但 S2 无 diff = **送达但未改** ⇒ 进递进 | Lead |
| **S2 修订** | 本人产出**一条技能修订**（写进**它自己的**技能目录，或它的 **SOUL**） | 它那两份落点（`$DSH_HOME/teamkit/roles/<name>/skills/**` 或 `$DSH_HOME/.teamkit/soul/<name>.md`，**以它人格段里给的绝对路径为准**）出现 diff，**mtime > `delivered_at`**，且指向 S0 点名的那条 | 本人 |
| **S3 复检** | 用 **S0 的同一条读数**重读 | **目标行为翻转**（同一条判据变真） | reviewer（Lead 裁定） |

### ★ S2 怎么**真写下去**（**踩过的坑：组织资产在工作区之外**）
你自己那几份（**SOUL / 岗位原则 / 角色技能**）都装在 `$DSH_HOME`（**不在你的项目目录里**）⇒
用 `write` 工具会被**沙箱拒**（实测逐字错误，两处都试过）：
```
Error: [sandbox: file access denied under workspace-write mode]
       [sandbox: escalation available — … the approval prompt asks the user]
```
⇒ **别用 `write`**，用插件给的**宿主侧工具**（由宿主代写，不受你的沙箱约束）：
| 工具 | 干什么 |
|---|---|
| `read_self {target}` | 读**你自己**的那一份 |
| `write_self {target, text, skill?, mode?, reason?}` | 写**你自己**的那一份。**默认追加**；整篇重写要显式 `mode:"replace"` |
**`target` 三选一**（**只有这三个，不接受任意路径** —— 它不是绕过沙箱的后门）：
| `target` | 落到哪 | 什么时候用 | 多快生效 |
|---|---|---|---|
| `soul` | `$DSH_HOME/.teamkit/soul/<你的名字>.md` | **我答应自己改什么**（被点名之后） | **下一步**（`agent/pre-step` 注入） |
| `principles` | `$DSH_HOME/teamkit/talents/principles/<你的角色>.md` | **这类活怎么干**（按角色共享） | 下次装配（走系统提示词） |
| `role-skill`（要带 `skill` 名） | `$DSH_HOME/teamkit/roles/<你的角色>/skills/<skill>/SKILL.md` | **我这条技能要改** | 磁盘技能根走 watcher，**当场生效** |
---

**闭环合上 = S1 ∧ S2 ∧ S3 全绿**。缺任一项 ⇒ 进**纠错递进**（N=2 轮起算）：
提醒 → 缩小范围 → 只留一条最重要的事 → 仍不动 ⇒ **换人**（收权/撤人，见上一节）。
> ⚠️ **"发消息"不等于"他会动"**（本项目实测：对 inactive 成员 `queued` 45s 后仍 inactive）
> ⇒ **S1 必须带窗口 `T`**，否则"永远没下一条输出"既判不了真也判不了假（**悬空态**）。
> ⚠️ **"写文件"不等于"下一轮进上下文"** ⇒ 生效路径三条（`PERF-LOOP.md` §4）：
> ① 他自己 `read`；② **磁盘技能根**（`skills/`）走 watcher ⇒ **当场生效**；
> ③ **SOUL** 走每步注入 ⇒ **下一步生效**。**改哪样，就想清楚它靠哪条路生效。**

**要硬门（可选、零代码）**：把"考核"建成一个任务，下游任务 `blocked_by` 它
⇒ **未过考核不得 claim**（真机制，见 `teamkit-review` 的就绪门）。

## 终止性（写死，不放权给模型）
- **层数 ≤ 3**；
- 每条线**轮次上限**（建议 3），到点必须上报；
- 每轮**必须**产出三态之一（接受/驳回/升级）——这就是"没有原地打转"的保证；
- 全局预算到点就收（时间/调用数），哪怕没做完，也要产出**当前最好状态 + 缺什么**。

## 无死锁（两条硬规矩）
1. **依赖无环**：新加的依赖会让图成环 → 当场拆（把环上最小那块合并给一个 owner）。
2. **每次等待都有主**：任何人说"等别人"，那个"别人"必须是一个**已存在的成员**，并且**有明确交付物**；
   否则这个等待就是死锁，改成"自己做 + 事后对齐"。

## 什么时候停下来问人（不要自己拍板）
- 要花真钱、要动生产、要对外发布、要删除不可恢复的东西；
- 需求本身矛盾（做 A 就做不了 B），且没有默认解；
- 你发现自己在**猜用户的意图**（而不是在解决技术问题）。
停下来不是失败：**"卡在需要人拍板的地方"是这个系统正常的一部分。**
