# 评审当门禁（默认模式）

## 先认清：DSH 没有评审原语
`team_task_update` 的动作里**没有** approve / review / verify —— **`complete` 是 owner 自证**。
所以这里的"评审门"是**协议**，不是机制：靠你（Lead/主管）在 `complete` 之前**要求**一次带证据的判决，
并把判决**落盘**。**别把它说成保证。**

## 判据先行
评审**不是**看它说得对不对，是看**判据**有没有被可观察的东西满足：
- 有**证据指针**（命令 + 读数 / 文件路径 / 前后差值）→ 才谈接受；
- 没证据的"我做完了" → 一律按**未完成**处理，但**别指责**，直接要证据。

## 三态判决（每轮必须落到其中之一，不许"再看看"）
| 判决 | 什么条件 | 输出 |
|---|---|---|
| **接受** | 判据被证据满足，且没有已知反例 | 一句话总结 + **证据指针** + 落盘位置 |
| **驳回** | 判据没满足，或证据与结论不符 | **具体差在哪 + 一个可执行的下一步**（不是"再试试"） |
| **升级** | 判据本身有问题 / 冲突无法在层内解决 / 需要人拍板 | 把问题**改写成一个决策问题**，交给上一层 |

「升级」不是失败，是这个系统的**安全阀** —— 它保证循环不会原地打转。

## 评审门（对应 OMC 的 completed → accepted）
**一个任务只有经过一次带证据的判决，才算"被批准"。** 五步：
1. 交付者回报 → 你**先要证据**，不先要结论；
2. **把"评审"建成一个任务**（`team_task_create`），别只写在文档里 —— 见下；
3. 判决**写进盘上**：逐条判据 + 证据指针 + 三态 + 下一步；
4. **下游任务只认"有判决记录"的上游** —— 上游只是 `complete` 而没有判决，下游**不许开工**；
5. **默认禁止自审**：派活的人不评自己派的活（原版 OMC 恰恰是派活者自审，**我们不抄**）。
   人不够时必须改判据：让评审者**只看证据文件**，不看交付者的自述。

### ⭐ 怎么让这道门**真的能拒绝**（零代码，实测依据）
DSH **没有** approve/review 原语，但**有一条原生硬门能骑**：
> **把"评审"建成一个任务，然后让下游任务 `blocked_by` **同时依赖交付任务与评审任务**。**
> 下游去 `claim` 时会被宿主的**就绪门硬拒**（`team task "…" is not ready to claim`）——
> 这是**实测被拒**的行为，不是建议。**结论：不需要写插件，也能把评审门从"协议"变成"硬门"。**

**两个前提（缺一个这条就退化成装饰）**
- **评审任务必须真的被建出来** —— **没有宿主钩子会自动建它，也没有任何自动巡检在盯着**（实测：本仓
  `plugin/` 里没有任何 task 巡检实现）。⇒ 只能靠**下面这张手动巡检表**，或者你自己写一个定时任务。
  ⚠️ 别把"有巡检告警"当成已经有了 —— 那是**要你去做的事**，不是现成的能力。
- **判决文件名要能对上任务**：`reviews/<task-id>.md`（带 task id），或在任务描述里写死路径。
  盘上若只按主题命名（`L1-research.md`、`playbook-v4.md`…），**任何"有判决才准 complete"的自动规则都会误拒每一次**。

### 手动巡检表（**照做即可；每一条都只用只读工具**）
在被问"门到底成不成立"之前，先跑一遍这四条：

| # | 拿什么读数 | 看到什么 ⇒ 说明什么 | 该做什么 |
|---|---|---|---|
| ① | `team_task_list`（任务 + status + blocked_by） | 有"评审"性质的任务，但**没有任何下游 `blocked_by` 它** | **门是装饰** ⇒ 建下游任务并把评审任务加进它的 `blocked_by` |
| ② | 同①，挑 `status: completed` 的 | 描述里要求了判决，但 `reviews/<task-id>.md` **不存在** | **"完成了但没判决"** ⇒ 补一次评审，或 reopen |
| ③ | 同①，找 `blocked_by` 指向**已完成**上游、而自己还是 `pending` | 上游早完成、下游还躺着 | **DSH 没有调度器** ⇒ **显式 `send_message` 叫醒**下游 |
| ④ | 同①，找互相 `blocked_by` 的环 | 两条任务互等 | **死锁** ⇒ 拆掉一条依赖（依赖只允许"上游→下游"） |

**判据（跑完要能回答）**：这次收尾里，**每一道评审门都有下游在 `blocked_by` 它**吗？
有一条没有 ⇒ **那道门不成立**（这正是"协议 vs 强制"的分界）。

> **实测附注（2026-09-14）**：① 这条**真能抓到**——建一个"…评审…"任务而不给下游，
> 巡检立刻报「门是装饰」；而给下游 `blocked_by` 之后，下游 `claim` 会被宿主硬拒
> （`team task "task-N" is not ready to claim`）。
> 另记一条**顺序约束**：**有下游依赖时 `delete` 任务会被拒**（`still blocks "task-4"`）
> ⇒ 清理要先删下游、再删上游。

### 还缺的一格：没有调度器
DSH **没有调度器**（`TeamTaskBoard` 只认 `journal + maxTasks`，连 roster 都不认识）→ **`complete` 不会唤醒下游**，
**Lead 必须自己当调度器**。所以：判决做完要**显式 `send_message` 叫醒下游**，别指望它自己动
（这条就是上面巡检表 ③ 的那一格）。

## `completed` → `accepted`：把判决**落到板上**（可照做）
底座**没有** `accepted` 态（`TeamTaskStatus` 只有 `pending / in_progress / completed / deleted` 四态）。
所以"**被批准**"这件事在我们这里是**两个东西拼出来的**：
> **`accepted` = `status === "completed"` 且 判决是 `accept`** —— **`completed` 本身不算被批准。**

**照做四步（每步都只用现成工具）**
1. **交付者 `complete` 之后**，评审者拿到证据指针；
2. **落的判决**：调 `review_task {task_id, verdict, note}` ——
   `verdict` 三选一（`accept` / `reject` / `none` 撤销），`note` **必填**（判决必须带理由）；
3. **看一眼**：调 `team_structure`（只读）⇒ 它直接给出每个任务的
   `parentTask` / `reviewState` / **`accepted`**。也可加 `only_pending_review:true`
   一眼看出"**完成了但还没判决**"的那些（那就是门漏了的地方）；
4. **要结构**（谁从谁切出来的）：调 `set_task_structure {task_id, parent_task, reason}`。
   **误设了就传空 `parent_task`** —— 那是"清掉这条结构"的回退路径（台账 append-only，**不删行**，仍可回放）。

**判决落在哪（两条都写，互为备份）**
- **台账**（盘上事实，append-only）：`<stateDir>/e2r.jsonl` ⇒ 可回放、可审计、**重启后重建**；
- **任务 `description` 末尾一行**：`【E²R】parent: task-12 · review: accept · note: …`
  ⇒ ⚠️ **这一行会出现在底座的 `team_task_list` 里**，因为 `description` 本来就是它的一个字段。
  ⇒ **"板上看得见结构"是这么来的 —— 不需要改底座的任何 schema。**

### ⚠️ 哪部分是**机制**、哪部分是**协议**（这一节不许读快）
| | 是什么 | 凭什么 |
|---|---|---|
| **依赖边 `blocked_by`** | ✅ **真机制** | `claim` 被宿主的就绪门**硬拒**（`team task "…" is not ready to claim`，真机实测）。**下游没满足依赖就进不去**。 |
| **分解边 `parentTask`** | ⚠️ **协议** | 底座**不认**这个字段。它不拒绝、不阻塞、不校验任何东西。 |
| **评审判决 `reviewState`** | ⚠️ **协议** | 同上。写了 `reject` 也**不会**阻止任何人继续 —— **没有任何底座代码读它**。 |

⇒ **一句话**：`review_task` 与 `set_task_structure` 提供的是**结构与判决的落点**（看得见、可审计），
**不是强制点**。**真拦住"没评审就往下走"的，只有一件事**：
**把"评审"建成一个任务，让下游 `blocked_by` 它** —— 那条才是上面表里第一行的硬门。

⇒ **所以别把 `reviewState: accept` 当成"门已经成立了"**。要门成立，必须**另外**有下游在 `blocked_by` 评审任务。
判据（自问自答）：**这次收尾里，每道评审门都有下游在 `blocked_by` 它吗？** 有一条没有 ⇒ 那道门不存在。

### 分解边 ≠ 依赖边（**别混用**）
- `blocked_by`（底座有）是 **`E_dep`**：管"**先做谁**"；
- `parentTask`（我们记的）是 **`E_tree`**：管"**由谁组成**"。
- **同一对节点上两者可能方向相反**（父任务往往要等子任务全完 ⇒ 父的 `blocked_by` 指向子；
  而结构上父是子的**上级**）。

⇒ **我们用 `blocked_by` 就能表达"谁先谁后"，但它不是 `E_tree` 的完整语义**；
  OMC 原版的分解边是**树的从属关系**，我们这里是**近似**。**别把近似说成等价。**

### 一句话给你的委托方
> **我们融合进来的**：结构（`parentTask`）与判决（`accept`/`reject`）**真的落盘、真的出现在板上**；
> **仍然只是协议的**：它们**不强制**任何事 —— 强制点只有底座的 `blocked_by` 就绪门。
> 想要"没评审就卡住"，就**建评审任务 + 下游 `blocked_by` 它**（照本节上面的四步）。

## 反驳自己一次（很便宜的鲁棒性）
接受之前问一句：**"如果这条是错的，最可能错在哪？"** 然后去看那一点。
硬门禁只认它被写进去的那些形状；评审能认**没被写进去的坏情况** —— 这就是选它当默认门禁的理由。

> `≤3` / `≤3` / `≤2` 三个数**都在原版里找得到**，而且**都有真拦点**（不是"定义了没用"）。
> ⚠️ 顺带避开一个**差点抄错的**：原版 `core/vessel_config.py:65` 有个 `max_subtask_depth = 2` ——
>   那个 **2** 是**子任务嵌套深度**，**不是"空转次数"**；两者同为 2 但**语义完全不同**。
>   （**同值不同义**是最容易抄错的一类 —— 本轮正是靠"逐条找拦点"才分辨出来。）

| 闸 | 数 | 到点怎么办 | 原版出处（**含真拦点**） |
|---|---|---|---|
| 每条线评审轮次 | **≤ 3** | 强制上报，不再原地重试 | `core/config.py:358` `MAX_REVIEW_ROUNDS=3`；拦点 `core/vessel.py:3177`（`review_count >= …` ⇒ 熔断并升级 CEO） |
| 同一任务驳回重试 | **≤ 3** | 第 3 次仍不过 → **升级**（改判据或换切分），不是第 4 次重试 | `core/vessel_config.py:62` `max_retries=3`（退避 `retry_delays=[5,15,30]`，`:63`） |
| 空转（报完成但没有可验证产出） | **≤ 2** | 打回一次；再空转 → 判失败并上报 | `core/vessel.py:175` `MAX_STALL_RETRIES: int = 2`；拦点 `core/vessel.py:1926-1948`（"说要派活却没派" ⇒ 计数 +1、回 `PROCESSING`、注入 nudge 要求直接调 `dispatch_child()`、`return` 跳过正常完成流程） |
| 全局预算 | 你自己定并写进 ROSTER | 到点产出"当前最好状态 + 缺什么"，哪怕没做完 | **无原版对应**（原版也没有全局预算闸 —— 这一条是我们加的） |

## 什么时候才点火硬门禁（strict）
只有下面任一成立才值得：
- 交付要**对外**（别人要按它办事）；
- 多域交叉、接口契约会被别人依赖；
- 出错的代价**不可逆**（数据 / 资金 / 发布）。

点火方式：`gate: strict` → 接 <上游适配器> 的 verify-gate（`gsd_workflow verify` / `gsd_cli`）。
**默认永远是 review。** 硬门禁是"我这次要一张签字纸"，不是"更专业"。
