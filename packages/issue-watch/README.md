# @dsh-external/dsh-issue-watch

每小时巡检指定仓库的 open issue / PR：新项自动分诊（PR 先本地验证再决定合并，issue 复现后修或给结论），结果落盘并回帖。

## 安装（**先读这一节：本包有两种装法，选错会"装了没反应"**）

### ⚠️ 关键前提：**本包不带 `dsh.bundle` 声明**

```
本包 `package.json` **没有** `dsh.bundle` 字段（可用 `npm pack`/解包后逐字核对）。
⇒ ★ 后果：**走"装配成 profile bundle"那条路 ⇒ 它不会激活**（不是报错，是**不生效**）。
⇒ ⇒ ★ 所以请走下面【方式 B】的注入路径，或【方式 A】里"显式装配"那条。
```
> 为什么会有这个差别：`dsh.bundle` 是**官方装配入口**要读的声明；
> 而**运行时注入**不走那个入口 ⇒ **不需要它**。
> （这两条路径的差别，我们是实测出来的：本机上这类包**都是靠注入激活**的。）

### 方式 A：Release 包（推荐，免构建）

从 [Releases](https://github.com/yjh051108/dsh-issue-watch/releases) 下载
`dsh-external-dsh-issue-watch-0.0.1.tgz` ⇒ 解压得到一个**含 `lib/` 的目录**，然后：

```bash
# 运行时注入（免重启）—— ★ 本包推荐这条（因为它没有 dsh.bundle）
# 对 AI 说：dev_inject_plugin <解压目录>
```

```bash
# 或"显式装配"进 profile（想让它随 profile 持久化时用）
#   ⚠️ 这条要求你的环境里**有能读 dsh.bundle 的装配入口**；本包没声明
#   ⇒ 若装配后**没生效** ⇒ 那正是上面那个前提在起作用，请改用注入路径
dsh plugin --profile web add <解压目录>
```

### 方式 B：git（需要你先构建出 `lib/`）

```bash
git clone https://github.com/yjh051108/dsh-issue-watch.git
DSH_CHECKOUT=<你的 DSH 源码检出> bash scripts/build.sh    # tsc → lib/
# 然后注入：dev_inject_plugin <clone 下来的目录>
```
> ⚠️ **`build.sh` 需要 DSH【源码】检出**（它要 `packages/` / `vendor/`）。
> **若你只有 npm 装的 dsh（`node_modules/@deepseek-ai/dsh`）⇒ 没有源码检出 ⇒ 这条走不通** ⇒ 请用方式 A。

## 怎么确认"真的装上了"

```
① 注入/装配**没有报错**（报错会指名是哪个包）
② ★ 让它做一次巡检 ⇒ **看有没有落盘记录**（本包会写台账；具体路径见 `lib/` 实现）
   ⚠️ 「未获取」：**精确的落盘路径与日志格式我没实测**（本 README 不是包的作者写的）——
     请以你跑出来的输出为准，若与上一句不符，**以实测为准**
③ 若"注入成功但没动静" ⇒ 先确认**注入器本身是否常驻**（本包靠它激活）
```
