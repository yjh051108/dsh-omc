# 运营：怎么让它跑起来、不卡死

> **这份文档解决三件事**：① 验收怎么才不是走过场 ② 怎么不被依赖卡死 ③ 断了之后怎么接上。
> **判据形态**：每条都给**能当场回答的问题**；答"不"的时候**有事发生**。

---

## 1. 「完成」与「被批准」是两件事

**问题**：执行者点了"完成"，**那不等于它做对了**。而"我觉得做完了"是返工的主要来源。

**⇒ 机制（不是流程）**：把"评审"本身**建成一条任务**，让下游任务**依赖它**。
```
下游去认领 ⇒ **会被系统直接拒绝**（不是靠人记得去评审）
```
**你会在真会话里看到的原文**（这就是"真门禁"的样子）：
```
task "task-N" is not ready to claim
```
**⇒ 判据**：
```
· **这条"完成"有验收人吗？**（没有 ⇒ 它还没完成）
· **验收人是不是产出者本人？**（是 ⇒ **形同没有评审** —— 判据：产出与验证必须分开）
· **验收的判据，是"技术验证"还是"验收裁定"？**
  ⇒ 两层要分清：
    · **技术验证** = 跑一遍、取读数、复现（**执行者/技术角色**做）
    · **验收裁定** = 够不够格（**负责人**做）
  ⇒ 一句话：**"可以怀疑，不可以代取读数"**
```

## 2. 三条"不卡死"的规矩

### 2.1 owner 不许留空（**这是死锁的头号成因**）

**现场**：上游任务被**释放了负责人**，而下游 `blocked_by` 它 ⇒ **永久卡死**（没人能认领）。
```
⇒ ★ **释放负责人的操作 ⇒ 先问：有没有下游在等它？**
  ⇒ 有 ⇒ **要么留人，要么把下游一起处理**（不许只做一半）
```
**⇒ 判据**：「你正要释放的这个 owner，**有没有下游 `blocked_by` 它？**」
答"有" ⇒ **停手**（或同时解决下游）。

### 2.2 依赖是**真门禁**，所以要写对

```
· 依赖写多了 ⇒ 明明能并行的事被串起来 ⇒ **白等**
· 依赖写少了 ⇒ 下游拿到半成品 ⇒ **返工**
⇒ 判据：「**B 真的需要 A 的产出吗？**」—— 需要**产出**才算依赖；需要"顺序感"不算。
```
**⚠️ 有真依赖时，别急着解**：
```
现场：曾把一条"写新内容"的任务挂在"先建仓"后面 ⇒ 其实**两者没有真依赖**
（写的东西进同一个暂存池，建仓时一并搬走即可）
⇒ 判据：「**没有它，我现在能开始吗？**」能 ⇒ **那不是真依赖**
```

### 2.3 卡住了怎么办（**三种情形，三种动作**）

```
① 有明确判据的事       ⇒ **谁负责谁裁**，不问任何人
② 跨域 / 协调的事       ⇒ 交给**唯一的跨域接口**（一个人，不是一圈人）
③ 卡住但上级不在        ⇒ **可以上达，但必须带"我试过什么"**
   ⚠️ 例外条件是"**上级确实不在了**"，**不是"我很急"**
⇒ 只有三类**事后必报最高层**：
   · 花预算 / 开人 / 设别人任务的依赖
   · 不可逆动作（开源 / 删数据 / 改宿主）
   · 跨辖区且接口裁不了的分歧
⇒ ★ **"想确认一下"不在三类里** —— 那是在把决策成本转嫁给上级。
```

## 3. 断了之后怎么接上（**重启 / 中断**）

**先分清两件事**（混在一起会让你修错地方）：
```
· **数据**（任务板 / 成员名单）—— 事件溯源 ⇒ **重启不丢**
· **人**（成员会话）—— **会断** ⇒ 需要"叫一下"或它自己回来
```

### 3.1 板能恢复（**这个可以放心**）
```
判据：重启后 → 任务条数 / 每条的状态与负责人 **与重启前一致**
（本公司实测：重启后板完整，差异 0）
```

### 3.2 被中断的任务 ⇒ **需要人接**
```
判据：「这条任务现在有没有人在做？」
  ⇒ 用**不依赖当前视角的证据**判断，不要只信一个状态字段
```
> ★★ **一条会让你误判的读数**（我们真栽过）：
> 那个状态字段 `inactive` **不是"它坏了"** —— 它是底座在"读不到"时填的**兜底值**。
> ```
> 实测：一个成员**一直在写日志**（日志时间在动），而状态显示 `inactive`。
> ⇒ 判据：**"看到 inactive" ⇒ 再看一眼"它的日志在不在动"**，两者合并再下结论。
> ⇒ 反过来说：**"它没动作" 也不等于 "它不在"** —— 它可能在编辑一个还没保存的文件。
> ```
> **⇒ 正解**：**叫一次**（发条消息）。
> **回了 ⇒ 不是孤儿**（哪怕状态仍是 inactive）；**叫不动 ⇒ 才是真需要换人**。

### 3.3 目标（goal）需要人重新打开 ⇒ **这是设计，不是 bug**
```
现象：会话重启后，goal 会变"未武装"状态
根因：底座**故意**这样（防止"无人授权就自动续跑"）
⇒ 所以它**不会自己恢复** ⇒ **需要一次显式的"恢复"动作**
⇒ 判据：「这个 goal 现在是武装状态吗？」不在 ⇒ **它需要一次 resume**
```
> ⚠️ **"自动恢复"是另一个选项，但它越过了底座的设计意图** ⇒
> **那是产品决策**（要用户明确接受"无人授权也可能续跑"的风险），**不是技术默认**。

## 4. 运行时的两条"省着用"（**上下文就是钱**）

```
① ★ **看一眼就要花的读数，别重复取**
   ⇒ 判据：「这个数我刚才取过吗？」取过 ⇒ **复用，别重跑**
② ★★ **"准备"不等于"做了"**
   现场：把文件改好了、验证也过了，**但没提交** ⇒ 对别人来说（和对外部世界）**它不存在**
   ⇒ 判据：「**我从用户/下游的位置往回看，能看见它吗？**」
   ⇒ 这条有四层，**每层的失败都不报错**：
     ① 本地有 ≠ ② 打包里有 ≠ ③ 公开仓里有 ≠ ④ 用户装上了
     （现场：白名单**静默**排除 · 安装器**静默**跳过 · `--check` 静默放行）
```

## 5. 运营期的"最小巡检"（**每周一次，五个问题**）

```
① 板子上有没有 **owner 空着但下游在等** 的？（有 ⇒ 立刻补）
② 有没有任务 **卡在同一个 owner 身上超过一轮**？（有 ⇒ 那是关键路径 ⇒ 见 K3）
③ 有没有"完成"但**没有验收记录**的？（有 ⇒ 见 §1）
④ 有没有 **owner 显示 inactive** 的？⇒ **叫一次**再看（别直接判死）
⑤ 有没有 **判据里写死的真值**已经过期？（有 ⇒ 改成现算 ⇒ 见 `CRITERIA.md` K14）
```
