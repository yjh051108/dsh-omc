```

   ⚠️ 反面教材就是我自己：我给公司加的锁（`ORG.md §1.2` 自我约束）**一次都没拦住我**，

   **"它让谁更专注在什么垂直领域上？"** 答不出 ⇒ 这条纪律就是成本

#### ★★ 1.2.1 为什么"自己 verify"是错的（**外部依据 + 我们的账**）
```
【外部依据】SQA 的定义性要求：验证必须由**未参与产出的人**做 ——
  「源码应当能被 **verification experts not involved in the software development process** 读懂」
  （[Software Quality Assurance](https://www.sciencedirect.com/topics/engineering/software-quality-assurance)）
⇒ **我参与了产出**（我定判据、我裁决）⇒ **按定义我不能再当验证者**
⇒ 而最坏的不是浪费，是：**我的读数会覆盖它的读数，然后没人再独立复核我**
   —— `P0` 事故就是这个链：**我越权 → 板坏 → 我又自己修 → 更坏**
```

#### ★★★ 1.2.4 正解：**我把两层混成一层了**（COO 判，CEO 批 / 2026-09-15）
**委托方**：「**凭什么你 verify**？……连底下的做技术的来做行不行啊？」
**我原以为**：要我"少 verify" ⇒ **错。** 正解是**我把两层混成一层了**：
```
【第 1 层 · 技术验证（取读数 / 复现）】← ★ **委托方要的就是这一层**
   产出者：任何执行者；验证者：**技术验证岗**；产出物：**原始读数 + 复现步骤**
   判据：**同样命令、同样环境，得到同样的数**
【第 2 层 · 验收裁定（够不够 / 批不批）】
   裁定者：上级 / 总监（`D-6`：「验收权在总监，点击权在 owner」）；产出物：**判决**
【CEO】**不取读数**（第 1 层给验证岗）；
   只在**①跨辖区 ②不可逆/对外**时终审，**且只读别人给的读数**
```
⇒ **一句话判据**：**「CEO 可以"怀疑"，不可以"代取"」** —— 怀疑 ⇒ **打回验证岗重取**。
⇒ ⚠️ **这条收口了我先前那个不完整的"例外②"**（我曾写"核对原始性也是 verification"）：
   **「核对原始性」属第 2 层（验收的一个动作），不属第 1 层。**

### D-6 · **上报链：CEO 不是转接口**（2026-09-14 委托方当场纠正）

委托方原话：
> 「**你为什么他只能给你说呀，他不能给总监上交吗？这么多事情都是你管吗？**

**定死**：
```
· 执行者 → 交付给【它的总监】           ⇒ 总监验收 → **总监自己批 complete**
· 总监   → 只把【结论 + 关键读数】报 CEO  ⇒ CEO 复核
· **CEO 不做"转接口"** —— 谁的下级谁管，谁的活谁批
```
**理由**：
- 委托方点出的成本是**真实的**：若每件事都经 CEO 转，
  **CEO 的上下文会被"转发"吃掉**，而转发**不产生任何价值**（信息在中间被压缩一次）。
- 与 **D-4** 一致：**管理者的产出是判据 + 人 + 节奏** —— **"批 complete"就是"判据是否达成"的裁决**，
  那正是**该由总监做的**。

**CEO 只保留三类介入**（**例外清单，不是默认流程**）：
1. **跨辖区**的事（要动别仓 / 要和解另一位总监）
2. **花预算 / 开人 / 设别人的任务依赖**（只有 Lead 能做的动作）
3. **独立复核**（抽查，不是逐件）

⚠️ **反面教材（本公司真实发生）**：
`product-director` 曾写「把退出码发我复核，**我核完再报 complete**」——
把"批 complete"挂给了 CEO。**已被纠正**：它自己核、**自己批**。
（它能自己写 prompt、能自己验收、能自己裁 —— **本来就有这个能力**。）

#### ⚠️ **D-6 的机制约束**（2026-09-14 实测，`product-director` + `e2r-landing` 各出一手读数）

**`claim` / `edit` / `complete` / `reopen` / `release` 全都要求「你必须是该任务的 owner」，或者你是 Lead。**
```
它建了 task-75（无主）后自己 complete  ⇒ ❌ Error: task mutation requires its owner or Team Lead
它 complete 自己持有的 task-69          ⇒ ✅ rev 8

★ 执行者把路径核成了真调读数（`D6-COMPLETE-AUTH.md`）：
  执行者 claim → complete → **reopen**（**owner 被清空**）→ 总监 claim → 总监 complete → delete
  ⇒ **总监真的成了能批的人，全程不需要 Lead**
  ⚠️ CEO 给的线索（走 `release`）**错了一步**：`release` 只在 `in_progress` 可用 ⇒
      **正解是 `reopen`（它自己就清 owner）**。执行者没照抄线索，核出来纠正了 CEO。
```
⇒ **定死**：
```
① 任务本来就归总监持有（总监 claim 过） ⇒ 总监直接 complete
② 任务是执行者持有的 ⇒ **执行者自己 complete**（那是它的权）
   ⇒ 总监要**亲手批**，须：执行者 `reopen`（交还 owner）→ 总监 `claim` → 总监 `complete`
   ⇒ 或总监只**验收把关**（不达标就 `reopen` / 不给过）
```
⇒ 一句话：**"能批" ≠ "能替它按按钮"。验收权在总监，点击权在 owner。**
（Lead 的 `reassign` 可转移 owner —— **那是例外手段，不是流程**。）

        ⇒ **走自己的上级 → 上级走 COO**（跨域唯一接口）
        ⇒ **不许直接发给 CEO**

【例外 · 只有这四类算"紧急"，可直发 CEO】
  ① 服务/进程挂了（面板、插件、宿主不可用）
  ② 数据被破坏或即将被破坏
  ③ 有人正在做不可逆 / 破坏性动作
  ④ 阻塞到无法工作，且上级也不在
  ⚠️ **"我觉得急""想快点"不算紧急**
  ⚠️ 报紧急时**必须写明是上面哪一类**（不写类别 ⇒ 不算紧急）
```

#### COO 的岗位（**为此而设**）
| | |
|---|---|
| **定位** | **跨域唯一接口**；管两位总监（产品总监 / 总工程师）及其下级 |
| **接什么** | 跨域汇报 · 撞车仲裁（同文件 / 浏览器锁）· 节奏（谁何时交什么）· 编制建议（报 CEO 开人） |
| **不接什么** | **辖区内的活**（那是总监的）· **为产出而读数**（D-1：要改代码就派人） |
| **对 CEO** | **只报结论 + 关键读数**；**它自己也不许跨域汇报**（除那四类紧急） |

#### 扩编（委托方口径：**走流程就行，不用像公司那么麻烦**）
```
① 谁需要人 ⇒ 报它的总监（写给"要什么角色 + 判据"，**不是"要个人你看着办"**）
② 总监 ⇒ 报 COO ⇒ COO 报 CEO ⇒ **CEO 开人**（`spawn_teammate` 只有 Lead 能做）
⇒ **两步到三步，不需要更多审批**
✅ 正面样本（已发生）：`product-director` **自己把 prompt 写好**才来要人 ⇒ CEO 照着开即可
```

**`claim` / `edit` / `complete` / `reopen` 全都要求「你必须是该任务的 owner」，或者你是 Lead。**
```
它建了 task-75（无主）后自己 complete  ⇒ ❌ Error: task mutation requires its owner or Team Lead
它 complete 自己持有的 task-69          ⇒ ✅ rev 8
```
⇒ **D-6 的正确落地形态只有两种**：
```
① 任务本来就归总监持有（总监 claim 过） ⇒ 总监直接 complete
② 任务是执行者持有的                ⇒ **执行者自己 complete**（那是它的权）
   ⇒ 总监的"批" = **验收把关**（读数不达标就 reopen / 不给过）
   ⇒ **总监不需要"替它按按钮"** —— **"能批" ≠ "能替它按按钮"**
```
⇒ **所以"CEO 不是转接口"与"总监不能一键批别人的任务"两件事并存，不矛盾**：
**验收权在总监，点击权在 owner。**（Lead 可用 `reassign` 转移 owner —— 那是**例外手段**，不是流程。）

## 7. ★★ 授权级数（**学来的** · 2026-09-14 / 详见 `MANAGEMENT.md` §一）

> **来源**：[6 Levels of AI Delegation](https://www.metaltoad.com/blog/6-levels-of-ai-delegation-a-framework-for-ai-management)（Metal Toad）
> **原文那句就是我们的病根**：
> 「**必须明确说清你要的是哪一级** —— 因为人不一样、任务也不一样。」

### 7.1 六级（**派活时必须写明**）
| 级 | 授权语 | 用在哪 |
|---|---|---|
| **1** | 去查，报告，**我来决定** | 高风险决策 |
| **2** | 去查，报**备选 + 利弊 + 你的建议** | 重要、需第二视角 |
| **3** | 告诉我你打算怎么做，**我不点头就别动** | 有行动权但要闸 |
| **4** | 告诉我你打算怎么做，**我没说不行就做** | 已建立信任 |
| **5** | 去做，**做完告诉我** | 低风险、可回退 |
| **6** | 去做，**不用再联系我** | 重复、无足轻重 |

### 7.2 我们**按角色×风险**定死（**这就是过去缺的那张表**）
| 角色 | 对谁 / 什么 | 级数 |
|---|---|---|
| **CEO** | **一切"产出性"动作**（写代码 / 脚本 / 跑探针 / 改盘上数据） | **不使用 1–6 级的自理权** —— 见 `§1.2` 例外清单；**动手即越权** |
| **CEO** | 对总监 | **2 级**（要备选 + 利弊 + 建议） |
| **总监** | 对其辖区执行者 · **非破坏性** | **4 级** |
| **总监** | 对其辖区执行者 · **破坏性 / 不可逆** | **3 级**（先报再动） |
| **执行者** | 自己辖区内常规活 | **4–5 级** |
| **任何人** | ⚠️ **对"会被持久化的共享对象 / 生产数据 / 宿主进程"** | **3 级 + 必须有回退物** |

⚠️ **两条硬规矩**：
1. **派活时不写级数 ⇒ 默认 3 级**（最保守）。
2. ⚠️ **P0 事故（`§1.1`）正是因为"对生产数据用了 5 级"** —— 这张表本该早就存在。

### 7.3 为什么这张表是**根因修复**而不是禁令
```
P0 事故的组织责任 = CEO（我认）
**系统条件** = **我们从来没有"授权级数"这个概念**
  ⇒ 所有人都只能凭感觉决定"这事我能不能自己动"
  ⇒ 我凭感觉对自己发了 5 级；总监凭感觉自己跑探针；执行者也一样
⇒ 光写"CEO 不许动手"**只是禁令**（治标）；
  **有了级数表 + 派活必写级数** ⇒ 让"该不该动手"变成**可以被检查的字段**（治本）
  —— 这正是外部复盘标准说的「**追究系统条件，不只追究个人**」（`MANAGEMENT.md` §三）
```
